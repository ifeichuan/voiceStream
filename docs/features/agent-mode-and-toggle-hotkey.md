# Agent 模式与切换式录音热键方案

## 背景

当前 VoiceStream 已具备以下能力：

- 全局快捷键触发录音
- 实时音频采集
- Aliyun Bailian 流式 STT
- 原生 HUD 实时展示录音与转写状态
- 通过 `pi --mode rpc` 对转写结果做整理
- 自动将结果粘贴回当前焦点输入框

但现阶段存在两个明显体验问题：

1. 录音快捷键必须按住才能录音，长时间使用负担较高
2. 录音结束后的 optimize 阶段耗时偏长，影响整体即时感

同时，产品方向上希望进一步演进为类似“贾维斯”的对话式任务代理：

- 用户直接说一句话
- 系统识别这是普通输入，还是一个可执行任务
- 若为任务，则自动在本地新建会话并后台执行
- 开始时即时反馈“已开始处理”
- 完成后主动通知用户

本文档用于记录该方案，作为后续实现参考。

## 当前实现现状

### 录音热键

当前全局快捷键为：

- `Cmd+Shift+Space`

当前行为是典型的 hold-to-talk：

- `Pressed`：开始录音
- `Released`：停止录音，并进入后处理流程

对应实现位于：

- `src-tauri/src/lib.rs`

### 当前后处理链路

录音结束后，当前链路如下：

1. 停止录音
2. 等待 STT 收尾，拿到最终文本
3. 调用 `pi --mode rpc` 执行文本整理
4. 将整理结果粘贴到当前输入位置

其中，文本整理逻辑位于：

- `src-tauri/src/pi_rpc.rs`

### optimize 慢的主要原因

经代码排查，当前慢点并不主要说明“RPC 模式本身有问题”，而是当前 RPC 使用方式较重。

当前每次 optimize 都会：

1. 新启动一个 `pi --mode rpc --no-session` 子进程
2. 写入 `set_auto_retry`
3. 写入 `prompt`
4. 等待完整的流式响应直到 `agent_end`
5. 再尝试补读最终文本
6. 结束后销毁子进程

这意味着每次录音结束后都要重新经历：

- 进程启动
- provider/model 初始化
- prompt 执行
- 会话结束

对于高频、短文本、低延迟场景，这种“一次请求一个进程”的方式成本较高。

### STT 链路判断

当前 STT 使用的是 WebSocket 流式识别：

- 录音过程中不断推送音频 chunk
- 停止录音后仅等待最终文本收尾

因此用户体感中的主要等待时间，更大概率集中在：

- STT 最终收尾
- `pi` 文本整理
- 粘贴前等待

其中最值得优先优化的是 `pi` 的调用方式。

## 目标体验

## 目标一：录音热键改为切换式

将当前“按住录音，松开结束”改为：

- 第一次按下：开始录音
- 第二次按下：结束录音

预期收益：

- 降低长按负担
- 更符合多数语音助手和录音工具习惯
- 更适合后续扩展出“普通输入模式”和“Agent 模式”两类入口

### 建议交互

保留当前默认快捷键：

- `Cmd+Shift+Space`

行为调整为：

- `Pressed`：切换录音状态
- `Released`：忽略

### 状态流转

- `idle -> recording`
- `recording -> processing`
- `processing -> pasted` 或 `error`

在切换式模式下，应避免重复按键导致的竞态问题，例如：

- processing 阶段再次按下时是否允许重新录音
- 正在录音时再次按下应只触发 stop，不应重复 start

## 目标二：先优化现有 dictation 链路，再评估多 provider

### 判断原则

在现阶段，不建议第一步就引入完整的多 AI provider 抽象，因为：

- 当前最大的延迟来源更像是链路结构问题，而不是 provider 缺失
- 直接引入 provider 层会增加工程复杂度
- 但短期收益不一定高于“常驻 RPC + session 复用”

### 优先优化方向

#### 1. 将 `pi` 改为常驻 RPC 进程

建议引入一个常驻 `PiRpcClient`：

- 应用启动时拉起一次 `pi --mode rpc`
- 持续保持 stdin/stdout 通道
- 每次文本整理直接复用该进程
- 不再为每次 optimize 单独启动和销毁进程

预期收益：

- 降低进程启动开销
- 降低 provider/model 初始化成本
- 显著改善短文本场景的响应时间

#### 2. 复用 session，而不是固定 `--no-session`

对高频整理场景，至少应复用进程；进一步可考虑复用 session。

对 Agent 任务场景，则建议显式使用：

- `new_session`
- `set_session_name`

这样可以：

- 在本地形成明确的任务会话
- 为“后台执行”和“完成后追踪结果”提供基础

#### 3. 增加耗时埋点

在真正优化前，应先测量，避免误判。

建议埋点：

- 录音开始时间
- 录音结束时间
- STT final 收到时间
- optimize 开始时间
- optimize 首字返回时间
- optimize 完成时间
- paste 开始/结束时间

建议输出到：

- Rust 日志
- 前端开发日志面板
- 后续可考虑持久化到本地诊断日志

#### 4. 支持“跳过 optimize”或轻量模式

对普通语音输入来说，目标通常是“尽快回填到当前输入框”。

因此可考虑提供：

- 直接粘贴原始转写
- 本地规则轻清洗
- LLM 整理可选开启

这有助于显著降低平均响应时间。

### 是否要引入 AI provider 接口

结论：

- 值得预留抽象
- 但不建议作为第一优先级

可先设计轻量接口，例如：

- `TextRefiner`
- `TaskAgent`

初始实现仍可只有：

- `PiRpcRefiner`
- `PiRpcTaskAgent`

待常驻 RPC 跑通、体验稳定后，再接入其他 provider。

## 目标三：增加 Agent 模式入口

除了普通 dictation 模式，还需要一个专门的 Agent 调用快捷键。

### 建议模式拆分

#### 模式 A：Dictation 模式

用途：

- 快速语音输入
- 结果直接进入当前焦点输入框

推荐入口：

- `Cmd+Shift+Space`

建议流程：

1. 第一次按下开始录音
2. 第二次按下停止录音
3. STT 生成文本
4. 执行轻量整理或快速 optimize
5. 自动粘贴到当前输入框

设计目标：

- 极快
- 低打扰
- 适合高频使用

#### 模式 B：Agent 模式

用途：

- 将一句自然语言识别为任务
- 在本地创建会话并后台执行
- 完成后主动通知用户

推荐入口（待定）：

- `Cmd+Shift+Enter`
- 或 `Cmd+Shift+A`

建议流程：

1. 第一次按下开始录音
2. 第二次按下结束录音
3. STT 得到文本
4. 对文本做任务识别
5. 若判断为任务，则本地新建 session
6. 在后台执行 agent
7. 立即向用户反馈“已开始处理”
8. 完成后发送通知，并可选语音播报

## Jarvis 风格 Agent 体验设计

## 设计原则

目标不是做一个聊天框，而是让系统表现得像一个“可随叫随用的后台执行代理”。

用户体验重点：

- 不需要先打开应用窗口
- 不需要手动管理复杂会话
- 说出任务后立即被接管
- 系统会主动告知“我开始做了”
- 系统在完成后会主动回来通知

### 核心体验

用户说：

- “帮我整理一下今天会议纪要”
- “在本地新建一个会话，然后后台执行这个任务”
- “查一下 optimize 为什么这么慢，给我一个排查方案”

系统应表现为：

1. 听懂内容
2. 判断这是一个任务
3. 创建本地会话
4. 进入后台执行
5. 立即反馈开始状态
6. 完成时主动通知

---

## Agent 模式建议链路

### 阶段 1：任务识别

先对语音转写内容做一次轻量判断，输出如下结构：

- 是否为可执行任务
- 任务标题
- 给用户的确认短语
- 后台执行用的任务描述

这样可以避免把所有内容都直接丢进重型 Agent 流程。

### 阶段 2：本地创建会话

对于确认是任务的内容，调用 pi RPC：

- `new_session`
- `set_session_name`

这里的 session 代表：

- 本地可追踪任务
- 后台执行上下文
- 后续通知的归属对象

### 阶段 3：后台执行

在新 session 中发送 prompt，触发 Agent 工作流。

建议要求：

- 不阻塞主录音交互线程
- 支持持续接收事件流
- 可提取开始、工具调用、最终结束状态

### 阶段 4：即时反馈

任务一旦进入后台，应立即给用户一个反馈。

反馈形式建议分层：

#### 文本 HUD

例如：

- “收到，正在处理…”
- “已创建任务，开始执行…”
- “已经开始行动。”

#### 可选语音反馈

在 macOS 上可先使用系统 `say` 命令作为 MVP：

- “好的，开始处理。”
- “任务已接收。”

### 阶段 5：完成通知

任务完成后，应主动通知用户。

建议支持：

#### 系统通知

例如：

- 标题：任务已完成
- 正文：已完成“排查 optimize 耗时原因”

#### 可选语音播报

例如：

- “任务已经完成。”

如果任务失败，也应有失败通知。

---

## 实时回传要求

用户明确希望：

- 刚开始执行时，系统就应实时返回一些文字
- 或直接播放一段语音，表示已经开始行动

这意味着 Agent 模式不应只在结束时一次性返回结果，而应支持至少两类增量反馈：

### 1. 开始反馈

一进入任务执行，即返回：

- 开始文案
- 或开始提示音 / TTS

### 2. 执行中反馈

后续可以逐步增强为：

- 流式短文本状态
- 工具调用摘要
- 当前执行阶段提示

例如：

- “正在读取项目文件…”
- “正在排查 RPC 调用链…”
- “正在整理结论…”

MVP 阶段可以先只做：

- 开始提示
- 完成通知

执行中细粒度状态可作为后续增强项。

---

## Prompt 设计建议

当前 dictation optimize prompt 是“文本整理助手”定位，这与 Agent 模式目标不同。

因此建议将两类 prompt 分离：

### A. Dictation Prompt

用途：

- 纠错
- 去口语化
- 去冗余
- 生成可直接粘贴的中性文本

目标：

- 快速
- 保守
- 不做复杂任务推理

### B. Agent Prompt

用途：

- 判断是否是任务
- 在新建本地会话中后台执行
- 像助手一样接管任务并汇报状态

目标：

- 面向任务执行
- 强调会话创建与后台运行
- 强调开始反馈与完成通知

建议不要用单个 prompt 同时承担“文本整理”和“任务代理”两种角色。

## 分阶段落地建议

## Phase 1：低风险体验优化

目标：先把当前主链路做顺。

建议实现：

1. 将录音热键改为 toggle 模式
2. 增加链路耗时埋点
3. 将 `pi` 调用从“每次单独启动”改为“常驻 RPC 进程”
4. 评估是否增加“跳过 optimize / 轻量整理”选项

验收标准：

- 用户不必按住录音
- 能量化识别慢点位置
- dictation 模式明显更快

## Phase 2：Agent 模式 MVP

目标：先跑通最小可用的“Jarvis 工作流”。

建议实现：

1. 新增 Agent 快捷键
2. 新增任务识别 prompt
3. 调用 `new_session` 创建本地会话
4. 在后台执行 prompt
5. 开始时显示 HUD 文案
6. 完成后发送系统通知

验收标准：

- 用户可以通过另一个快捷键发起任务
- 任务会进入后台执行
- 用户可收到开始反馈和完成通知

## Phase 3：增强 Jarvis 感

建议增强：

1. 加入开始语音反馈
2. 执行中流式状态回传
3. 最近任务列表 / 任务中心
4. 失败重试与错误摘要
5. provider 抽象与多模型策略

## 当前结论

当前阶段最合理的推进顺序是：

1. 先把录音快捷键从“按住”改成“切换式”
2. 先排查并优化现有 `pi` 调用方式，优先考虑常驻 RPC 和 session 复用
3. 暂缓把重点放在“新增 AI provider 接口”上，但为后续抽象预留空间
4. 在此基础上增加独立的 Agent 快捷键，逐步演进到 Jarvis 风格的后台任务代理

简而言之：

> 先把当前语音输入链路做快、做顺，再把任务代理能力叠加上去。
