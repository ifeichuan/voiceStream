# Agent 模式与切换式录音热键

## 背景

当前 SpeakMore 已具备以下能力:

- 全局快捷键触发录音
- 实时音频采集
- Aliyun Bailian 流式 STT
- 原生 HUD 实时展示录音与转写状态
- 通过 `pi --mode rpc` 对转写结果做整理
- 自动将结果粘贴回当前焦点输入框

但现阶段存在两个明显体验问题:

1. 录音快捷键必须按住才能录音,长时间使用负担较高
2. 录音结束后的 optimize 阶段耗时偏长,影响整体即时感

同时,产品方向上希望进一步演进为类似"贾维斯"的对话式任务代理:

- 用户直接说一句话
- 系统识别这是普通输入,还是一个可执行任务
- 若为任务,则自动在本地新建会话并后台执行
- 开始时即时反馈"已开始处理"
- 完成后主动通知用户

本文档用于记录当前实现状态、已验证结论,以及下一步产品演进方向。

---

## 当前实现现状

### 录音热键

当前全局快捷键为:

- `Cmd+Shift+Space`

当前实现已经演进为 hybrid 模式:

- 长按:按下开始录音,松手结束
- 轻按:点按一次进入锁定录音,再按一次并松手结束

对应实现位于:

- `src-tauri/src/lib.rs`

该交互保留了 hold-to-talk 的直觉性,也兼顾了长时间说话时无需持续按住的体验。

### 当前后处理链路

录音结束后,当前链路如下:

1. 停止录音
2. 等待 STT 收尾,拿到最终文本
3. 调用 `pi --mode rpc` 执行文本整理
4. 将整理结果粘贴到当前输入位置

其中,文本整理逻辑位于:

- `src-tauri/src/pi_rpc.rs`

### optimize 慢的主要原因

前期排查表明,慢点并不主要来自"RPC 模式本身不可用",而是调用方式是否足够轻。

当前实现已经演进为分模式策略:

#### DictationFast 当前实现

默认的普通输入链路使用:

- 预启动一个 `pi --mode rpc` 进程
- 复用同一个 RPC 子进程
- 每次请求前显式调用一次 `new_session`
- 然后再发送 `prompt`
- 不加载 extensions / skills / prompt templates / themes
- 不使用长期 session 污染普通输入

这条链路的目标是:

- 保留进程复用带来的低延迟
- 避免历史会话污染普通 dictation
- 将普通输入和 Agent 任务链路彻底分开

#### Agent 模式

- `AgentSession`：保留固定 session，适合后台任务执行

当前普通输入只保留 `DictationFast` 链路，位于：

- `src-tauri/src/pi_rpc.rs`

并支持通过环境变量切换:

- `SPEAKMORE_PI_MODE=dictation-fast`
- `SPEAKMORE_PI_MODE=agent`

### STT 链路判断

当前 STT 使用的是 WebSocket 流式识别:

- 录音过程中不断推送音频 chunk
- 停止录音后仅等待最终文本收尾

因此用户体感中的主要等待时间,更大概率集中在:

- STT 最终收尾
- `pi` 文本整理
- 粘贴前等待

其中最值得优先优化的是 `pi` 的调用方式。

## 当前方向

## 方向一:录音热键优化

将原先单一的"按住录音,松开结束"优化为 hybrid 交互:

- 长按时:按下开始录音,松手结束
- 轻按时:点按一次锁定录音,再按一次并松手结束

预期收益:

- 降低长按负担
- 更符合多数语音助手和录音工具习惯
- 更适合后续扩展出"普通输入模式"和"Agent 模式"两类入口

### 建议交互

保留当前默认快捷键:

- `Cmd+Shift+Space`

行为调整为:

- `Pressed`:切换录音状态
- `Released`:忽略

### 状态流转

- `idle -> recording`
- `recording -> processing`
- `processing -> pasted` 或 `error`

在切换式模式下,应避免重复按键导致的竞态问题,例如:

- processing 阶段再次按下时是否允许重新录音
- 正在录音时再次按下应只触发 stop,不应重复 start

---

## 方向二:先优化现有 dictation 链路,再评估多 provider

### 当前阶段结论

这一阶段已经得到比较明确的工程结论:

- 对普通 dictation 来说,不应复用长期 session
- 但应尽量复用已经启动的 `pi --mode rpc` 进程
- 每次请求前调用 `new_session`,几乎没有明显额外成本
- 预启动 + 进程复用,相比每次 fresh process,实测大约能带来约 30% 的性能收益
- 在当前实验里,`aliyun-bailian / qwen3.5-flash` 是更适合 DictationFast 的组合

### 判断原则

在现阶段,不建议第一步就引入完整的多 AI provider 抽象,因为:

- 当前最大的延迟来源更像是链路结构问题,而不是 provider 缺失
- 直接引入 provider 层会增加工程复杂度
- 但短期收益不一定高于"常驻 RPC + session 复用"

### 优先优化方向

#### 1. 将 `pi` 改为预启动 + 可复用 RPC 进程

这一点已经做了最小可用实现:

- 应用启动时执行 `warmup()`
- 默认 `DictationFast` 路径复用同一个 RPC 子进程
- 通过 `SPEAKMORE_PI_REUSE_PROCESS` 可切换成 fresh process,对比基准表现

当前观察:

- 进程复用在 DictationFast 上是有效的
- 第一次请求仍可能带一点冷启动余波
- 但后续请求明显更快

#### 2. 普通输入不复用长期 session,但每次请求显式 `new_session`

当前的 DictationFast 实现不是长期复用同一个 session,而是:

- 复用进程
- 每次请求前调用一次 `new_session`

这样可以同时满足:

- 避免历史上下文污染普通输入
- 保留进程复用的性能收益

对 Agent 任务场景,则仍建议显式使用:

- `new_session`
- `set_session_name`

以形成明确的任务会话与后台执行上下文。

#### 3. 增加耗时埋点

在真正优化前,应先测量,避免误判。

建议埋点:

- 录音开始时间
- 录音结束时间
- STT final 收到时间
- optimize 开始时间
- optimize 首字返回时间
- optimize 完成时间
- paste 开始/结束时间

建议输出到:

- Rust 日志
- 前端开发日志面板
- 后续可考虑持久化到本地诊断日志

#### 4. 支持"跳过 optimize"或轻量模式

对普通语音输入来说,目标通常是"尽快回填到当前输入框"。

因此当前方向仍然成立:

- 直接粘贴原始转写
- 本地规则轻清洗
- LLM 整理可选开启

其中当前已经落地了一条更轻的 LLM 路径:

- `DictationFast`
- 更保守的 prompt
- 不加载扩展环境
- 适合作为默认 dictation optimize 路径

### 是否要引入 AI provider 接口

结论:

- 值得预留抽象
- 但不建议作为第一优先级

可先设计轻量接口,例如:

- `TextRefiner`
- `TaskAgent`

初始实现仍可只有:

- `PiRpcRefiner`
- `PiRpcTaskAgent`

待 DictationFast 和 Agent 路径完全稳定后,再继续扩展其他 provider。

### 当前开发辅助命令

仓库中已新增脚本:

- `scripts/speakmore-dev.sh`

当前常用命令包括:

- `scripts/speakmore-dev.sh dev-fast`
- `scripts/speakmore-dev.sh dev-voice`
- `scripts/speakmore-dev.sh dev-agent`
- `scripts/speakmore-dev.sh bench 10`
- `scripts/speakmore-dev.sh bench-fresh 10`

这些命令用于快速验证:

- 默认 DictationFast 启动
- Agent 模式
- 复用进程 vs fresh process 的真实性能差异

## 方向三:增加 Agent 模式入口

除了普通 dictation 模式,还需要一个专门的 Agent 调用快捷键。

### 建议模式拆分

#### 模式 A:Dictation 模式

用途:

- 快速语音输入
- 结果直接进入当前焦点输入框
- 追求低延迟、低干扰、可预测

推荐入口:

- `Cmd+Shift+Space`

会话策略:

- 默认不使用长生命周期 agent 会话
- 可直接走轻量 LLM refine,或走一次性 `pi --mode rpc` 文本整理
- 不应把连续多次普通输入都写进同一个长期 session

建议流程:

1. 第一次按下开始录音
2. 第二次按下停止录音
3. STT 生成文本
4. 执行轻量整理或快速 optimize
5. 自动粘贴到当前输入框

设计目标:

- 极快
- 低打扰
- 适合高频使用

#### 模式 B:Agent 模式

用途:

- 将一句自然语言识别为任务
- 在本地创建固定会话并后台执行
- 完成后主动通知用户
- 支持较长任务和多步工具调用

典型任务示例:

- "帮我把桌面文件整理一下"
- "把下载目录里重复文件找出来,整理完后告诉我"
- "帮我检查这个项目的性能瓶颈,跑完之后主动通知我"

推荐入口(当前仍待定):

- `Cmd+Shift+Enter`
- 或 `Cmd+Shift+A`

会话策略:

- Agent 模式应创建并复用一个明确的任务 session
- 该 session 用于承载任务上下文、工具调用记录、阶段性进展和最终结果
- 与 Dictation 模式分离,不与普通输入共用长期 session

建议流程:

1. 第一次按下开始录音
2. 第二次按下结束录音
3. STT 得到文本
4. 对文本做任务识别
5. 若判断为任务,则本地新建固定 session,并写入任务标题或摘要
6. 在后台执行 agent
7. 立即向用户反馈"已开始处理"或其他极短开始提示
8. 即使用户切走当前窗口,任务也继续进行
9. 完成后发送通知,并可选语音播报

## Jarvis 风格 Agent 体验设计

## 设计原则

目标不是做一个聊天框,而是让系统表现得像一个"可随叫随用的后台执行代理"。

用户体验重点:

- 不需要先打开应用窗口
- 不需要手动管理复杂会话
- 说出任务后立即被接管
- 系统会主动告知"我开始做了"
- 系统在完成后会主动回来通知

### 核心体验

用户说:

- "帮我整理一下今天会议纪要"
- "在本地新建一个会话,然后后台执行这个任务"
- "查一下 optimize 为什么这么慢,给我一个排查方案"

系统应表现为:

1. 听懂内容
2. 判断这是一个任务
3. 创建本地会话
4. 进入后台执行
5. 立即反馈开始状态
6. 完成时主动通知

### 产品特性:后台任务型 Agent

该模式不是"说一句话然后立刻粘贴结果",而是把用户语音作为一个真正的后台任务入口。

关键特征:

- 用户通过单独快捷键进入 Agent 模式
- 系统为该任务创建固定 session,而不是复用普通输入链路
- 任务可持续运行,不要求用户停留在当前窗口
- 任务执行完成后主动通知用户
- 适合文件整理、项目检查、批处理、信息收集等需要一段时间的任务

一个典型例子:

- 用户说:`你帮我把本地桌面文件整理一下,整理完告诉我`
- 系统行为:
  1. 创建任务 session
  2. 立即反馈"已开始处理"
  3. 在后台持续运行整理任务
  4. 完成后通过通知中心、HUD 或语音主动提醒用户

这类任务链路应与普通 Dictation 完全分离:

- Dictation:追求极快、低延迟、一次性整理后直接粘贴
- Agent:追求可持续执行、会话承载、后台运行和任务完成通知

---

## Agent 模式下一步建议链路

### 阶段 1:任务识别

先对语音转写内容做一次轻量判断,输出如下结构:

- 是否为可执行任务
- 任务标题
- 给用户的确认短语
- 后台执行用的任务描述

这样可以避免把所有内容都直接丢进重型 Agent 流程。

### 阶段 2:本地创建会话

对于确认是任务的内容,调用 pi RPC:

- `new_session`
- `set_session_name`

这里的 session 代表:

- 本地可追踪任务
- 后台执行上下文
- 后续通知的归属对象

### 阶段 3:后台执行

在新 session 中发送 prompt,触发 Agent 工作流。

建议要求:

- 不阻塞主录音交互线程
- 支持持续接收事件流
- 可提取开始、工具调用、最终结束状态

### 阶段 4:即时反馈

任务一旦进入后台,应立即给用户一个反馈。

反馈形式建议分层:

#### 文本 HUD

例如:

- "收到,正在处理..."
- "已创建任务,开始执行..."
- "已经开始行动。"

#### 可选语音播报

在 macOS 上可先使用系统 `say` 命令作为 MVP:

- "好的,开始处理。"
- "任务已接收。"

### 阶段 5:完成通知

任务完成后,应主动通知用户。

建议支持:

#### 系统通知

例如:

- 标题:任务已完成
- 正文:已完成"排查 optimize 耗时原因"

#### 可选语音播报

例如:

- "任务已经完成。"

如果任务失败,也应有失败通知。

---

## 实时回传要求

用户明确希望:

- 刚开始执行时,系统就应实时返回一些文字
- 或直接播放一段语音,表示已经开始行动

这意味着 Agent 模式不应只在结束时一次性返回结果,而应支持至少两类增量反馈:

### 1. 开始反馈

一进入任务执行,即返回:

- 开始文案
- 或开始提示音 / TTS

### 2. 执行中反馈

后续可以逐步增强为:

- 流式短文本状态
- 工具调用摘要
- 当前执行阶段提示

例如:

- "正在读取项目文件..."
- "正在排查 RPC 调用链..."
- "正在整理结论..."

MVP 阶段可以先只做:

- 开始提示
- 完成通知

执行中细粒度状态可作为后续增强项。

## Prompt 设计建议

当前 dictation optimize prompt 是"文本整理助手"定位,这与 Agent 模式目标不同。

因此建议将两类 prompt 分离:

### A. Dictation Prompt

用途:

- 纠错
- 去口语化
- 去冗余
- 生成可直接粘贴的中性文本

目标:

- 快速
- 保守
- 不做复杂任务推理

### B. Agent Prompt

用途:

- 判断是否是任务
- 在新建本地会话中后台执行
- 像助手一样接管任务并汇报状态

目标:

- 面向任务执行
- 强调会话创建与后台运行
- 强调开始反馈与完成通知

建议不要用单个 prompt 同时承担"文本整理"和"任务代理"两种角色。

## 分阶段落地建议

## Phase 1:低风险体验优化

目标:先把当前主链路做顺。

建议实现:

1. 将录音热键改为 toggle 模式
2. 增加链路耗时埋点
3. 将 `pi` 调用从"每次单独启动"改为"常驻 RPC 进程"
4. 评估是否增加"跳过 optimize / 轻量整理"选项

验收标准:

- 用户不必按住录音
- 能量化识别慢点位置
- dictation 模式明显更快

## Phase 2:Agent 模式 MVP

目标:先跑通最小可用的"Jarvis 工作流"。

建议实现:

1. 新增 Agent 快捷键
2. 新增任务识别 prompt
3. 调用 `new_session` 创建本地会话
4. 在后台执行 prompt
5. 开始时显示 HUD 文案
6. 完成后发送系统通知

验收标准:

- 用户可以通过另一个快捷键发起任务
- 任务会进入后台执行
- 用户可收到开始反馈和完成通知

## Phase 3:增强 Jarvis 感

建议增强:

1. 加入开始播报
2. 执行中流式状态回传
3. 最近任务列表 / 任务中心
4. 失败重试与错误摘要
5. provider 抽象与多模型策略

## 当前结论

当前阶段最合理的推进顺序是:

1. 先把录音快捷键从"按住"改成"切换式"
2. 先排查并优化现有 `pi` 调用方式,优先考虑常驻 RPC 和 session 复用
3. 暂缓把重点放在"新增 AI provider 接口"上,但为后续抽象预留空间
4. 在此基础上增加独立的 Agent 快捷键,逐步演进到 Jarvis 风格的后台任务代理

简而言之:

> 先把当前语音输入链路做快、做顺,再把任务代理能力叠加上去。
